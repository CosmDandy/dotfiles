# Безопасность DevOps

Прикладной свод для одного инженера с **публичными** инфраструктурными репозиториями (dotfiles, homelab, IaC). Про секреты — отдельно в [secrets.md](secrets.md); здесь то, что вокруг: гейты в CI, supply chain, контейнеры, IaC-практики.

Собрано веб-исследованием (июль 2026), фаза перекрёстной проверки не отрабатывала — факты из источников, но без состязательной верификации. Инциденты 2026 года особенно стоит перепроверять по первоисточникам.

## Ландшафт инструментов: что живо в 2025-2026

Половина «стандартных» IaC-сканеров мертва — это первое, что надо знать:

| Инструмент | Статус | Что делать |
|---|---|---|
| **Terrascan** | ☠️ архивирован Tenable 2025-11-20, последний релиз 09.2024 | не брать; преемника вендор не назвал |
| **tfsec** | ⚠️ свёрнут в Trivy, только maintenance | мигрировать: `tfsec .` → `trivy config .`, ID проверок (`AVD-*`) те же |
| **Trivy** | ✅ активен | **основной выбор**: IaC + образы + зависимости + секреты + живой кластер в одном бинаре |
| **Checkov** | ✅ активен (Palo Alto) | брать ради графового анализа связей между ресурсами и комплаенс-отчётов |
| **KICS** | ✅ активен (Checkmarx) | 2400+ проверок, много форматов; нишевый выбор |

Различие Trivy и Checkov — в классе возможностей, не в числе правил: Checkov умеет **межресурсный граф** (800+ graph-checks), но не сканирует образы и живые кластеры; Trivy наоборот. Кастомные политики: Python/YAML у Checkov, Rego у Trivy.

Отдельно: **TFLint — линтер, а не сканер** (устаревший синтаксис, ошибки провайдера), он дополняет, а не заменяет security-скан.

**Урок про выбор инструментов:** у Terrascan было 5.2k звёзд на момент архивации. Звёзды — не сигнал живости, смотри дату последнего релиза и статус мейнтейнера.

## Сканеры сами стали вектором атаки

Март–апрель 2026, группа TeamPCP — два инцидента подряд, оба через кражу publisher-кредов, без единого 0-day:

- **Trivy**: атакующие force-push'ем переписали **75 из 76 тегов версий**, пайплайны с `@v0.x` начали выгружать секреты.
- **KICS**: перезаписаны теги в Docker Hub (`latest`, `v2.1.20`, `alpine`, `debian`). Отравленный бинарь **сканировал нормально**, но слал результаты на `audit.checkmarx[.]cx`.

Ключевое следствие: **вывод IaC-сканера сам по себе чувствителен** — он содержит топологию инфраструктуры, имена ресурсов, иногда секреты из манифестов. Компрометация защитного гейта сливает то, что он защищал.

Отсюда пиннинг по SHA/digest — базовая гигиена, а не паранойя. И CI-раннер надо считать зоной поражения кредов: при инциденте ротируется всё, до чего он дотягивался.

## Пиннинг и cooldown

**Только полный 40-символьный commit SHA неизменяем** — это позиция GitHub из официальной документации. Теги и ветки перемещаются владельцем репозитория:

```yaml
uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
```

Как ломали на практике (`tj-actions/changed-files`, 23 000+ репозиториев): PAT мейнтейнера SpotBugs утёк через `pull_request_target` → доступ к reviewdog → переписаны теги → скомпрометирован зависящий от него `tj-actions`. Вредонос дампил креды из памяти раннера в логи. **Мутабельность тегов — механизм атаки.**

С августа 2025 GitHub умеет **принудительный SHA-пиннинг** политикой репозитория/организации: непиннутые workflow падают, а не предупреждают.

**Cooldown 7–14 дней** на обновления зависимостей и actions (`pinact --min-age 7`, Renovate `minimumReleaseAge`) блокирует большинство supply-chain атак — их обычно выявляют быстрее чем за неделю. Обновление пинов автоматизируется через Dependabot/Renovate, а не отменяется ради удобства.

## Триггеры и pwn request

`pull_request_target` выполняется в контексте **базового** репозитория: доступны секреты, `GITHUB_TOKEN` по умолчанию с правом записи, и на публичном репо это запускается **без одобрения мейнтейнера**. Классический pwn request — чекаут кода PR (`ref: github.event.pull_request.head.sha`) внутри такой джобы.

Тонкости, которые ломают наивную защиту:

- Даже **без единого секрета** джоба эксплуатируема: read/write `GITHUB_TOKEN` лежит в памяти раннера.
- `actions/checkout` **по умолчанию пишет токен на диск** (`persist-credentials: true`) — любой последующий шаг его прочитает. Ставь `persist-credentials: false`.
- Не нужен явный `run` вредоносного кода: хватит обычной сборки — атакующий правит `package.json`/Makefile, срабатывают `npm preinstall`/`postinstall`.

**Безопасная архитектура** — два workflow: непривилегированный на `pull_request` собирает и тестирует недоверенный код, кладёт результат в артефакт; отдельный на `workflow_run` с правами и секретами разбирает артефакт.

С июня 2026 `actions/checkout` v7 **блокирует чекаут fork-PR** внутри `pull_request_target`/`workflow_run` по умолчанию (забэкпортировано в старые мажоры). Опт-аут `allow-unsafe-pr-checkout` делает решение видимым в файле. Но защита узкая: не покрывает чекаут других недоверенных репозиториев и `git`/`gh` вручную.

**Никогда не подключай self-hosted runner к публичному репозиторию** — любой может открыть PR и скомпрометировать среду раннера.

## Публичные репозитории: что даётся бесплатно

Аргумент в пользу «публично по умолчанию» — лучший тулинг достаётся даром:

| Возможность | Публичные | Приватные |
|---|---|---|
| Secret scanning + **push protection** | бесплатно | GHAS (платно) |
| CodeQL (SAST), dependency review | бесплатно | GHAS |
| **Artifact attestations** (SLSA-провенанс) | Free/Pro/Team | только Enterprise |
| Dependabot alerts, rulesets, advisories | бесплатно на всех планах | |

Платный GHAS добавляет только инкремент (AI-детект секретов, кастомные паттерны, Copilot Autofix) — для базовой гигиены на личном публичном репо он не нужен.

**Secret scanning и push protection на публичных репозиториях включены по умолчанию** — отдельно настраивать нечего, в том числе в новых репо из шаблона. Проверка состояния:

```sh
gh api repos/<owner>/<repo> \
  --jq '.security_and_analysis | {secret_scanning, secret_scanning_push_protection}'
```

Настройки репозитория (в отличие от файлов) **не наследуются от template-репозитория** — шаблон тиражирует только содержимое. Всё, что нужно единообразно на всех репо, должно жить файлом в шаблоне; остальное — включать отдельно или скриптом через `gh api`.

**Keyless-подпись образов** (cosign + OIDC GitHub): приватного ключа не существует вообще, подпись через OIDC-токен раннера, есть в стартовом workflow «Publish Docker Container». Метаданные пишутся в публичный лог прозрачности Rekor (имя пользователя, репо, workflow) — для приватных это утечка и потому выключено по умолчанию, **для публичных возражение снимается**. Подпись решает подмену образа в реестре, но не уязвимости внутри — это к Trivy.

## zizmor: анализ самих workflow

Нишу «безопасность CI-конфигов» Trivy/Checkov не покрывают вообще. [zizmor](https://github.com/zizmorcore/zizmor) (Trail of Bits, MIT) ловит: непиннутые `uses:`, template injection, опасные триггеры, избыточные `permissions`, `secrets: inherit`, cache poisoning, утечку git-кредов в артефакты (`artipacked`).

Почему дёшево внедрить: работает **офлайн без токена**, 16 из 50 проверок чинятся автоматом через `--fix` (включая SHA-пиннинг), отдаёт SARIF в GitHub Security tab, умеет собирать pre-commit конфиги.

## Контейнеры и dev-контейнеры

**Секреты в слои — никогда.** `ARG`/`ENV` для этого непригодны (значения остаются в образе) — это позиция самой Docker. Правильный путь — BuildKit secret mounts: `RUN --mount=type=secret,id=x`, секрет виден только на время инструкции. Для приватных git-зависимостей есть `--mount=type=ssh` и предопределённые `GIT_AUTH_TOKEN`. Инцидент CodeCov начался ровно с кредов, забытых в образе.

**Монтирование `/var/run/docker.sock` OWASP приравнивает к передаче root на хосте.** Паттерн `docker-outside-of-docker` в devcontainer — осознанное решение о доверии, а не удобная мелочь.

**Dev container features опасны по умолчанию:**
- `install.sh` каждой фичи выполняется **от root** при сборке — это чужой код с рутом;
- без явной версии подставляется `:latest` — непиннутое поведение;
- фича сама может запросить `privileged`, capabilities, seccomp-опции и монтирование томов;
- пиннинг по OCI-digest поддерживается (`baz@sha256:...`), у HTTPS-тарболов — нет.

Базовый хардненинг OWASP: непривилегированный пользователь, `--cap-drop=ALL` и добавить нужное, `--security-opt=no-new-privileges`, seccomp/AppArmor, лимиты памяти/CPU/PIDs, `--read-only` где возможно, rootless-режим демона.

## IaC-практики

**Terraform state — plaintext-секрет.** У OpenTofu есть встроенное шифрование **state и plan** (не зависит от бэкенда). Для одного инженера без облачного KMS — PBKDF2 с парольной фразой: минимум 16 символов, ≥200 000 итераций (по умолчанию 600 000), опция `enforced` гарантирует, что незашифрованное не запишется. Границы: не защищает от потери данных и от replay старого state; тот, кто запускает apply, всё равно видит секреты.

**Proxmox API-токены:** privilege separation включена по умолчанию — токену нужны свои ACL, а его эффективные права = **пересечение** прав токена и владельца, так что превысить юзера он не может. Секрет показывается **один раз**, ротация = удалить и создать заново. Права давать на конкретный путь/пул, а не на датацентр.

**Kubernetes:**
- **Pod Security Standards** — три готовых профиля: Privileged / Baseline / Restricted. Разумный минимум — Baseline везде, Restricted где можно. Restricted требует `runAsNonRoot: true` и `allowPrivilegeEscalation: false` и ограничивает типы томов так, что примонтировать docker.sock или hostPath становится нельзя структурно. Внедряется через Pod Security Admission по namespace в режимах `warn`/`audit`/`enforce` — можно катить постепенно.
- **NetworkPolicy**: под без политики разрешает **весь** трафик — default-deny вводится явно (пустой `podSelector: {}` + оба `policyTypes`), причём **на каждый namespace отдельно**. Критично: без поддерживающего CNI (Cilium, Calico, Antrea…) объект политики **не делает ничего** — «политика создана» ≠ «трафик ограничен». Исключения: трафик к/от узла всегда разрешён, под не может заблокировать сам себя.
- **kube-bench** — CIS-проверка самого кластера (дополняет, а не заменяет сканы манифестов). Запускается разовым Job'ом. Выдаёт много WARN (в примере 57 PASS / 19 FAIL / 54 WARN) — **гейтить по exit code нельзя**, нужен триаж и базлайн исключений. Для нетиповых дистрибутивов (Talos) профиль подбирается вручную.

## Порядок внедрения

**Первая очередь** — дёшево и максимально эффективно:

1. **gitleaks в CI** (не только pre-commit: OWASP прямо пишет, что хук необходим, но недостаточен — нужен серверный бэкстоп)
2. **`trivy config`** — один сканер на IaC и образы
3. **zizmor** + пиннинг всех actions по SHA
4. `permissions: {}` на уровне workflow, явные гранты в job; `persist-credentials: false`
5. Запрет `pull_request_target` с чекаутом PR-кода; никаких self-hosted runner'ов на публичных репо
6. Branch protection + required review (кейс: кража $3M из-за правки адреса кошелька в ветке без обязательного ревью)

**Вторая очередь:** Renovate/Dependabot с cooldown 7–14 дней, cosign keyless для своих ghcr-образов, digest-пиннинг базовых образов и devcontainer features, Pod Security Standards в кластере.

**Не нужно:** SBOM/SLSA ради галочки. Сканирование **транзитивных** зависимостей — есть аргументированная контр-позиция (tl;dr sec): эксплуатируемость цепочки «свой код → прямая зависимость → уязвимая функция в транзитивной» низка, а чинить нечего — пакеты чужие. Исключение — события уровня log4shell.

## Что изучать

- **OpenSSF LFD121** «Developing Secure Software» — бесплатный, 14–18 часов, сертификат на 2 года. Тот же материал на edX (LFD104x/105x/106x), курс открыт на GitHub.
- **OWASP Top 10 CI/CD Security Risks** (CICD-SEC-1..10) — каноническая таксономия для threat modeling пайплайна. Осторожно: застряла на **v1.0 от 2022** — годится как концептуальная рамка, но не как источник актуальных инструментов.
- **OWASP Docker Security Cheat Sheet** — конкретный чеклист хардненинга контейнеров.
- Модель supply chain из трёх фаз (Source → Build → Packaging/Deployment) — удобна как порядок внедрения гейтов.
