# Модернизация инженерной среды на Pi Coding Agent

## Статус и границы согласования

Источник — исходное предложение владельца «Pi Coding Agent — Architecture &
Workflow Modernization». Это рабочая программа, а не утверждённый технический
план внедрения всех перечисленных компонентов.

2026-11-20: согласовано сохранить программу и выполнить первую задачу — подключить
существующий Knowledge MCP к Pi. Остальные архитектурные решения обсуждаются
до реализации. Gateway, SDD-фреймворк, новые модели и subagents пока не выбраны.

## Цель

Заменить настроенный Claude Code практичной, надёжной и понятной средой на Pi,
а не построить многоагентную платформу. Оптимизировать инженерный процесс,
а не число агентов или объём автоматизации.

Среда должна:

- Соблюдать установленные соглашения без повторных напоминаний.
- Сохранять непрерывность задач между сессиями и devcontainers.
- Экономно использовать инструменты, контекст и модельные вызовы.
- Поддерживать интерактивное обсуждение и автономное делегированное выполнение.
- Помогать сначала сформулировать задачу и принять решения, затем реализовывать.
- Использовать централизованные знания без новой фрагментированной памяти.
- Требовать минимум сопровождения и сохранять участие инженера в проектировании.

## Исходная среда

- Pi — основной агент; Claude Code и его CLAUDE.md — исходная поведенческая база.
- Основной доступ к OpenAI — подписка ChatGPT с Codex-совместимой авторизацией.
  Дополнительные API-расходы допустимы при измеримой пользе.
- Около 20 devcontainers, физические и виртуальные хосты, Tailscale/Headscale.
- Основные операции: Git, SSH, Kubernetes, Terraform, Ansible и CI/CD.
- Knowledge MCP уже работает: Obsidian — источник истины, централизованный сервер,
  SQLite FTS с BM25-подобным ранжированием и весами полей. Векторный поиск ранее
  оценивался и сейчас не является предпочтительным решением.

## Логические слои

1. **Runtime:** Pi, сессии, инструменты, инструкции, skills и расширения.
   Один основной агент и одна основная reasoning-модель на задачу.
2. **Контекст и знания:** рабочий контекст; сохраняемое состояние задачи
   (спецификация, решения, прогресс, неудачи, проверки); постоянные знания в vault.
   История разговора не должна быть единственным состоянием длительной задачи.
3. **Доступ к моделям:** подписочный доступ отдельно от API-доступа.
   Не считать OAuth подписки готовым основанием для общего API-сервиса.
4. **Инструменты:** Knowledge MCP, shell/filesystem, Git и инфраструктурные CLI,
   operational skills; Codemode и изолированные subagents только при пользе.
5. **Наблюдаемость:** вызовы, токены, cache usage, результаты задач и лишний рост
   контекста без обязательного сбора чувствительного содержимого.

## Направления работы

### WS1 — Перенос поведения Claude Code

Проверить CLAUDE.md и фактическую конфигурацию Pi. Для каждого соглашения определить
место: глобальные или проектные инструкции, skill, extension/hook либо
детерминированная настройка инструмента. Не переписывать правила ради стиля.

Сохранить краткую русскую коммуникацию, различие interactive/delegated,
запрет несогласованной реализации при обсуждении, автономное завершение
делегированной работы в согласованных границах, минимум chatter,
контекстно-экономную разведку, проверяемую definition of done, dry-run,
подтверждение production-операций, rollback и Knowledge MCP как источник знаний.

Результат: карта миграции и минимальная рабочая конфигурация Pi.

### WS2 — Конфигурация и авторизация для devcontainers

Сравнить общий каталог Pi, read-only конфигурацию с отдельными credentials,
безопасную доставку секретов и — только при необходимости — broker/gateway.
Учесть permissions, параллельные записи и refresh, утечку и отзыв credentials,
ограничения провайдера, независимые сессии и простое создание нового контейнера.

Результат: простейшая поддерживаемая схема без повторного login в каждом контейнере,
насколько это безопасно и поддерживается. Обычная конфигурация отделена от секретов.

### WS3 — Контекст и токены

Проверить историю, накопление tool results, compaction, переключение моделей,
prompt caching и доступный учёт подписки. Раздельно измерять общий объём токенов,
API-расходы и расход квоты ChatGPT — это не взаимозаменяемые величины.

Оценить стабильные инструкции и tool definitions, кэш одной модели,
селективный Knowledge retrieval, фильтрацию вывода, Codemode, изоляцию subagents,
compaction и отказ от ненужных переключений моделей. Для Codemode сравнить
реальную экономию с генерацией JavaScript, ошибками и задержкой исполнения.

Результат: приоритеты оптимизации, ожидаемый эффект, риски и метод измерения.

### WS4 — Specification-driven development

Рабочий цикл: Explore → Specify → Plan → Implement → Verify → Record.
Изучить OpenSpec и другие поддерживаемые решения, совместимые с Pi.
Не требовать спецификацию для тривиальных задач.

Для существенной работы нужны acceptance criteria, причины решений,
сохраняемый прогресс и восстановление после перерыва/compaction. Инженер участвует
в выборе решений, а обсуждение отделено от реализации. Спецификации и task state
живут рядом с проектом; долгоживущие знания предлагаются в vault без слепого
дублирования. Документация должна быть минимально достаточной.

Результат: выбранный workflow и, если оправдан, SDD-инструмент.

### WS5 — Codemode и оркестрация инструментов

Проверить именно установленную версию: native/extension, доступ к MCP tools,
среду исполнения и границы безопасности, параллелизм, ошибки, usage и latency.
Применять для фильтрации больших результатов, агрегации источников,
независимых параллельных операций и повторяемых структурированных процедур.
Простой прямой вызов не заменять JavaScript без причины.

Результат: проверенное подключение и практические правила использования.

### WS6 — Decision Models и лёгкое делегирование

Проверить модели и провайдеров, OpenRouter, native decision endpoints против chat,
схемы, форматы результатов, стоимость, latency, accuracy/calibration,
неоднозначные входы и совместимость с gateway. Сравнить с детерминированными
правилами и недорогой обычной LLM. Не вводить классификатор ради его наличия.
Вероятностный ответ никогда не разрешает разрушительную инфраструктурную операцию.

Результат: один обоснованный пилот и метод оценки пользы.

### WS7 — API gateway и телеметрия

Сравнить direct API, Radius, LiteLLM Proxy и лёгкие альтернативы при необходимости:
интеграция Pi, subscription auth, ключи, routing, provider/decision support,
cached/uncached usage, метрики сессии/проекта, self-hosting, безопасность,
надёжность, стоимость и сопровождение.

Gateway предпочтителен для API-billed моделей, если его польза оправдывает
эксплуатацию; подписочный трафик не направлять через него без подтверждённого
поддерживаемого основания. Наблюдаемость вводить ступенчато:
локальная статистика Pi → агрегированные метрики контейнеров → Langfuse или аналог,
только если необходим анализ на уровне задач.

Не сохранять prompts, secrets, credentials или инфраструктурные логи
без явно согласованных правил обработки данных.

Результат: минимальная архитектура gateway и наблюдаемости.

### WS8 — Подписка и расходы

Сравнить Plus, возможный переход на тариф $100/месяц, direct OpenAI API,
смешанный доступ, Decision Models и дешёвые модели для изолированных задач.
Использовать реальные измерения или явно помеченные оценки.

Учитывать input/output/cached input, reasoning/tool usage где доступны,
поведение квоты, compaction, subagent overhead, конкурентные сессии,
качество и задержку. Оптимизировать полезную инженерную работу на единицу стоимости,
а не минимальную сумму счёта; месячные расходы должны быть предсказуемыми.

Результат: break-even и рекомендация по провайдерам.

## Очерёдность

- **Фаза 0 — аудит:** версия, конфигурация, интеграции, авторизация и инструменты;
  проверка по установленному ПО и официальным источникам, без изменений.
- **Фаза 1 — рабочий минимум:** инструкции, Knowledge MCP, конфигурация,
  безопасная авторизация, основная coding-модель и проверка обычной разработки/ops.
  Критерий: надёжность и поведение сопоставимы с прежней средой Claude Code.
- **Фаза 2 — структурированная работа:** подходящий SDD, состояние задач,
  границы, acceptance criteria, проверки и resume.
  Критерий: существенная задача понятна и возобновляема между сессиями.
- **Фаза 3 — эффективность:** baseline, caching/compaction, селективный Codemode,
  меньше лишнего вывода, при необходимости лёгкие subagents.
  Критерий: измеримое сокращение потерь без ухудшения качества.
- **Фаза 4 — централизованный model access:** только обоснованный gateway,
  API credentials, метрики, один classifier pilot, экономика API/подписки.
  Критерий: дополнительная сложность приносит измеримую пользу.
- **Фаза 5 — улучшения по наблюдениям:** повторяющийся сбой → подходящий слой
  исправления → минимальная коррекция → проверка; не размножать правила.

## Первая задача — Knowledge MCP

Согласованный объём:

- [x] Подключить существующий сервер к пользовательской конфигурации Pi.
- [x] Читать существующий bearer token из отдельного файла, не копировать секрет
  в репозиторий, Nix store или командную строку.
- [x] Использовать native MCP Pi, без дополнительного adapter/gateway.
- [x] Проверить соединение, обнаружение инструментов и read-only поиск.
- [x] Сохранить воспроизводимую конфигурацию и указания по её применению.

Результат 2026-11-20: `knowledge` подключён локально через Streamable HTTP,
семь инструментов доступны через native `tool_search` (`deferred` exposure).
`pi mcp list --json` показывает `connected`, без ошибок. Тест
`tools/pi/tests/mcp.test.mjs --live` с `PI_TEST_MODULES` установленного Pi
проверил загрузку конфигурации, обработку токена и настоящий поиск без записи
в vault и без обращения к LLM. `instructions.test.mjs` также прошёл.
Шаблон — `tools/pi/mcp.json`; порядок подключения — `tools/pi/README.md`.
Распространение через Home Manager и удалённые контейнеры пока не внедрено.

Ограничения: не менять сервер, vault, токены, Claude Code, routing моделей,
остальные skills и правила. Не разворачивать изменения на удалённых хостах
в рамках этой задачи. Для уже открытой Pi-сессии потребуется `/reload`.

## План: строка состояния над редактором Pi

Реализовано:

- Имена выполняющихся инструментов показаны слева, рядом с режимом: `EXECUTE bash, read`. Между режимом и списком — пробел без точки. Имена приглушённо-серые, без путей и аргументов; параллельные вызовы одного инструмента не дублируют имя. После завершения последнего вызова список исчезает.
- `Pair` остаётся профилем по умолчанию, но `PAIR` не занимает место в строке. Из профилей виден только выбранный `AUTONOMOUS`. Меню выбора и поведение профилей не изменились.

- Справа три анимации без названий фаз: звезда с необязательным заголовком резюме, волна при ожидании или генерации, вращение во время выполнения инструмента. В покое и после прерывания — неподвижные `· Ready` и `■ Interrupted`. Внутренние события и измерение времени не меняются.

Проверка реализации: обычный и автономный профили, включённые Agents, параллельные инструменты с разным временем завершения, отсутствие устаревшей подписи в `Ready`, узкий терминал в обеих темах.

## Не-цели

Не строить иерархию агентов, не заменять Obsidian Knowledge MCP,
не заводить локальные memory systems, не требовать дорогой API без измерений,
не разворачивать local LLM без задачи, не вводить несколько gateways,
не усложнять доставку конфигурации и авторизацию без причины,
не превращать SDD в бумажную работу и не воспроизводить внутренности Claude Code,
если Pi предоставляет более простой механизм.

Архитектурные варианты обсуждать до окончательного плана реализации.
Подтверждённые возможности отделять от предположений; существующие соглашения
менять только по конкретной причине.
